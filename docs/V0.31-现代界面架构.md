# V0.31 现代界面架构

## 目标

V0.31 只升级界面工程和接口边界，不重写已经验证的规则引擎。新旧界面共享同一个 `GameEngine`、事件呈现器、存档目录和选择目录，避免形成两套互相漂移的游戏。

## 数据流

```text
React / TypeScript 界面
          ↓  /api/v1
FastAPI + Pydantic 兼容层
          ↓
现有 WebApplication 服务门面
          ↓
GameEngine / JSON 存档 / DOCX 规则源
```

## 前端职责

- React：组合角色、事件、抉择、行动和侧栏组件。
- TypeScript：约束接口数据结构，尽早暴露字段不一致。
- Tailwind CSS：提供构建期样式工具；成品视觉由项目自己的国风变量和组件样式控制。
- Radix UI：提供弹窗、悬浮提示等无障碍交互原语。
- Lucide：统一界面图标的尺寸、线宽和状态。
- Motion：只处理事件切换和按钮反馈，不接管游戏逻辑。
- TanStack Query：缓存服务端快照并在行动后原位更新。
- Zustand：只保存行动草稿、展开状态等纯界面数据。

## 后端职责

- FastAPI 只暴露版本化接口、校验请求并托管预构建前端。
- `WebApplication.perform_action` 是新旧界面的公共行动入口。
- `GameEngine` 继续独占时间、随机数、修为、战斗和存档结算。
- API 文档只在本机 `/api/docs` 开放，服务器仍只监听 `127.0.0.1`。

## 内容与数据库边界

当前仍不引入 SQLite：

- DOCX 保留为原始规则权威来源。
- JSON/YAML 适合版本化的事件、物品、NPC 原型和策划内容。
- JSON 存档继续保存单机动态状态，便于备份和迁移。
- 当动态 NPC 数量、跨存档索引或模组查询达到实际瓶颈后，再用仓储接口将动态数据迁移到 SQLite。

## 渐进迁移约束

1. 每迁移一类页面，都必须继续调用真实 API，不制作只供截图的平行组件。
2. V0.30 稳定界面至少保留到 V0.31 全页面流程验收完成。
3. 任何新界面问题都不能改变原有存档格式或随机结算结果。
4. 发布前必须通过 Python 回归、TypeScript 构建、前端测试和桌面/手机浏览器验收。
